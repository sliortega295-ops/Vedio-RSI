# Wan 完整单轮实验：结果与交付

本轮已经闭合，不是仍在等待 GPU。结论为 **NO_VALID_FRONTIER：没有通过质量验收的组合方案**。这不等于没有单项收益，也不等于复现了论文的完整结果。

单项中，EasyCache 0.03 在本轮五个 prompt 上从 927.573 秒降到 495.301 秒，1.873×，通过组件 gate 和 Master 独立检查。Kernel 融合为 1.172×。两种组合测到 2.205×、1.800×，但都出现新的中等级别画面伪影，不能作为成功加速结果。

### 为什么最终没有有效组合

Master 对每种组合均真实查看全部 15 张原定对比图，并在 prompt2 的门框/门面处查看对齐的完整分辨率帧。两种组合都有原 Dense 中没有的矩形块状纹理、横向接缝，最高 severity 为 medium。主对话另外实际查看了 Dense 与两组合在 prompt2/frame0 的三张对齐原图，复核到相同现象；这三张检查不替代 Master 的完整覆盖。

组件通过不能自动推出组合通过。浮点融合可能改变近似缓存的决策或轨迹，但本轮没有隔离定位原因，不能直接把伪影归因于某一个模块。也没有通过放松 gate、补一个未经实测的配方或把 identity 算成优化结果来填充最终 frontier。

Kernel 的“exact”是本轮沿用的数学/结构合同：保留原 attention/FFN、权重、scheduler 和逻辑工作，未做逐元素输出差异证明。每 prompt 的 50 steps、100 次 Python transformer forward 入口被记录；缓存可以在入口内返回，**100 个入口不等于 100 次完整 DiT 计算**，完整遍历数仍不可用。

### 执行队列不是全部瓶颈

已经明确提交、合法就绪的单 prompt 任务，采样没有观察到“有空卡却未派发”的机会（0 秒），但这不等于 Agent 完美利用资源：对最终确实提交的视频，任务图已 ready、尚未 submit 且存在空卡的采样墙钟约 **556.514 秒**，机会量 2,889.573 GPU-seconds。这包含可选探测、Agent 思考及主动等待，不能全部当作可无损删除的时间。必须分清执行层排队与 Agent 提交前的等待。

最后一批搜索生成结束至第一批组合开始间隔 29.126 分钟；最后生成结束至服务关闭还有 18.014 分钟。这里混有看图、源码检查、独立验证、传输和交付整理，不是两个可直接删掉的“纯串行 CPU 阶段”。

### API 与传图

三个会话共 678 次模型请求，其中 673 完成、5 次 transport error。请求时长累计 220.867 分钟，三会话可重叠；至少一条 API 请求活跃的并集为 120.595 分钟。模型请求包括推理、生成输出、传输和服务端处理，没有独立 RTT 拆分，**不能把这 120 分钟称为网络延迟**。

40 次图片传输/缓存事件累计 68.457 秒。中继请求 JSON 声明大小累计约 9.356 GB，含反复发送的上下文、图片及失败尝试；不是实际线路流量，也不是模型权重。外部模型下载为 0、经本机搬运权重为 0，不代表所有 API 网络流量为 0。Broker 错误还包括策略拒绝（例如 Executor 无权独立验收、禁止读取原始 MP4）和实现错误，不能全部归到 VPN。

因此，本轮未达到接近一小时目标；也不能凭 API 活跃区间推断关掉视觉评测就能在一小时内完成。与 SANA A 的模型和工作负载不同，**不报告因果 Harness 加速比**。

## 5. 故障与人工介入：没有无人闭环

1. 首轮 `001` 在正式基准前因错误的全模型 dtype 假设停止，PARTIAL_INFRA，墙钟 758.100 秒；保留，不计入 002 的模型结果。修复后的独立单视频 GPU 预检为 184.413 秒，也不进入正式基准或 Agent 输入。
2. 002 的验收器错误比较来自集合的 `_use_default_values` 列表顺序；真实 scheduler 数值/时间步没变。使用独立版本的比较补丁，原始回执和冻结代码未改。相同会话恢复、原 gate 请求逐字重送，暂停约 466.1 秒，没有重生成。
3. 并发适配层在最终归档时遍历可变候选字典，独立评估已成功但回执丢失。只修复归档快照，在原评估 SHA 和进程回执匹配后调和状态、读取原独立判断；没有重复 GPU/评估。暂停约 282.2 秒，含原已提交 GPU 波次继续工作的时间，不能全部视为纯停机。
4. 原生 Master 已明确写出完整 `NO_VALID_FRONTIER`，但外层要求另一个文件名；主对话将既有否决理由/证据机械序列化为 terminal 文件。未修改判断、没有新视频或验收结论。随后原 Controller 的负结果闭合检查实际通过。

两次恢复均保留原三会话、候选 ID、预算及冻结源码/配置。补丁放在独立版本的服务覆盖层，不声称部署始终是同一未修改程序。并发归档是**本项目适配层缺陷**，不是已证明的官方 Sol-Agent 缺陷。详见 [工程记录](ENGINEERING-VALIDATION.md)。

负结果 Controller 写 `NO-FRONTIER-CHECK.json`，而旧通用分析器只找正路径的 `method-search/CLOSURE-CHECK.json`。Wan 报告层读取实际负路径回执、核对原生空 frontier 和 delivery SHA，明确记录文件名差异；没有补造原生 closure 文件，也没有据此接受任何组合。最终审计 PASS 指证据/闭合/归档完整，不是最终优化通过。

## 6. Memory 和论文结论边界

15 次搜索尝试都有最终经验处理记录。10 次失败/拒绝有本轮证据；5 个通过独立组件检查的点仍为 `NOT_ADMITTED`，因为当前成功记忆入口要求根层最终独立审计/目标成功，而本轮组合为负结果。这不抹掉它们的组件证据，也不能改成已验证的集成成功经验。该状态粒度是以后需要改进的 Harness 接口，**本轮没有伪造成功写回**。

本轮支持：

- Harness 能在 Wan softmax attention 上完成六类来源筛查，并实际适配/运行外部融合、稀疏和量化代码，而不只是返回链接。
- 已找到五个本轮被接受并由 Master 独立检查的组件点，最快单项约 1.873×。
- 实测组合仍然必要；两项独立通过不能替代组合质量验收。
- 八卡执行并行已发生，但 Agent/接口/验收交付仍留下大间隔；只改 GPU 队列不足以证明端到端高效。

本轮不支持：搜索超越固定 Sol 菜单、稳定的最优 Wan recipe、完整论文数值复现、无人干预运行、跨模型/跨卡 Memory 改善、广泛质量保持或正式 rollout 因果加速。质量范围只有五 prompt/一个 seed；VBench、人工盲评、重复搜索种子、多模型对照、权重量化、few-step 视频及蒸馏训练均 NOT_RUN。完整 DiT 遍历计数和 native/Diffusers 输出等价也未证明。

后续最值得优先处理的是适配边界：给高价值稀疏/帧级调度方法补可信执行接口与依赖环境，给融合+缓存补组合数值/决策轨迹诊断；同时将组件成功、组合失败、适用条件分层写回。它们是下一轮建议，**本轮没有自行追加实验或放宽预算**。
