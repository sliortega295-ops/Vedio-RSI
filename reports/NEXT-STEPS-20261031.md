# 下一步：先证明能找到、用对、验真的新方法

状态：**建议 / NOT_RUN**。本次 PR 不启动实验，不预约 GPU，不下载模型，也不修改历史结果。下面是供选择方向的工作顺序，不是已经完成的承诺。

## 总体方向

保留三条主线：开放搜索、条件化经验、快速 rollout。当前先做前两条的基础：**以 Wan 为主要验证载体，把搜索发现转成可验收的方法；先校准质量判断，再讨论最终速度。** 暂不继续开发另一版复杂调度算法，也不直接再跑一整轮长时间自动搜索。

ResearchBoost 已提供 Codex + 技能 + 外部判定的相邻实现；仅说“我们给 Codex 一个 Harness”不足以形成差异。我们要回答的是：跨架构可用方法怎么选、组合何时失效、经验如何有条件迁移，以及达到可靠结果要花多少总成本。[借鉴与边界](RESEARCHBOOST-REVIEW-20261026.md)

## P0：先把质量和结果身份固定好

已有旧 Cache 的同产物复评分歧，以及 Wan 组件通过、组合失败。先审查这些现成证据，不急着生成更多视频。

交付要求：

- 固定质量 rubric、完整采样规则、评审输入格式、模型/设置和证据哈希；任何修改有新协议版本。
- 争议点保留两份判断。匿名重复评审或人工仲裁只用于校准，不能挑一个更有利的结论覆盖历史。
- 将 `component_validated`、`composition_rejected`、`quality_disputed`、`implementation_unverified` 分开；根级失败不应抹掉组件证据，组件通过也不能自动批准组合。
- 方法检查、算子数值、采样图像质量、完整视频质量分别报告。无逐位测试就不写 bitwise lossless。

完成标志：每个候选的状态与支持证据可追溯；固定产物上的评审分歧有可执行处理规则。需要新 API 评审或 GPU 对照时另列成本并确认执行，不在本发布任务中运行。

## P1：让全新搜索会话证明不是靠人工喂名单

先做 search-only，六类仍完整保留：Kernel、Cache、Sparse Attention、Quantization、Token Pruning、Few-step。

- 主控整理的 41 项目录作为**审计参照**，不要作为新 Agent 的启动答案。初始输入只给模型结构、硬件、工作负载、方法范围和通用检索策略。
- 按机制词、模型词、作者项目、框架索引展开；明确分页和停止条件。已知方法名查证与开放发现分别计数。
- 每类输出论文身份、官方/第三方来源、固定 commit 的真实实现入口、许可证状态、硬件/训练/权重约束与未解决问题。
- 分清“找到论文”“找到代码”“适用于当前合同”“算子路径跑通”“全视频通过”。下载模型或训练需求不得被偷偷纳入原实验。
- 其他五类补足广度，不把 sparse 的主控调试成绩推广到所有类别。尚未穷尽时保留待查队列，不宣称完整召回率。

完成标志：得到新会话可审计的发现与筛选轨迹；有足够不同机制的候选进入静态适配。此阶段不承诺任何速度数字，也不把作者报告值写成本地经验。

## P2：选 3–5 个机制不同的外部方法，先短验证再全流程

候选由 P1 的证据决定；本报告不预定最终 recipe。优先考虑有 Wan 与 Ampere 实现证据、许可清晰、无需改权重和步数的路线。现有目录中的名字只说明有调查空间，不是要求 Agent 必须选这些方法。

| 验证层 | 必须回答的问题 | 通过后才做什么 |
|---|---|---|
| 静态适配 | 真实实现在哪，接口/shape/CFG/硬件是否匹配？ | 冻结 candidate、来源和适配 diff |
| 算子/DiT 探测 | 实际命中目标 kernel 吗？是否有 fallback？误差、构建与单次成本多少？ | 正式视频，不将模块收益冒充整视频收益 |
| 单方法完整验证 | 原五 prompt/seed、50 步/权重合同和全部适用检查是否通过？ | 独立验收与可组合组件记录 |
| 组合验证 | 新方法与 Cache/Kernel 是否相互干扰？ | 最终交付；失败仍保留完整轨迹 |

不能把“前面做了短验证”当作删掉完整流程的理由。正式搜索仍需提出、实现、预检、生成、质量、反馈、独立验证、组合和交付。把低成本预检用于筛除明显不适用实现，不放宽最终质量标准。

VSA 等需要训练的稀疏方法、蒸馏 few-step、不同权重 checkpoint 单开轨道，记录训练/准备成本与各自 Dense/原生 baseline。它们不能与固定 50-step 原权重实验混算加速。

Wan 当前只证明权重张量映射一致；恢复新实验前还应补 tokenizer/runtime 与原生输出的适配一致性检查。若发现语义不一致，先修正并重新冻结 baseline，修正本身不计优化收益。

## P3：Memory 存条件与失败原因，不存无条件捷径

最低记录：模型/attention 结构、权重与源码 revision、GPU/软件环境、工作负载、方法机制、具体实现、实际激活证据、质量判定版本、适用条件、失败原因、时间分解和组合兼容性。

区分纯静态知识与本地实测经验；`NOT_RUN`、`DISPUTED_QUALITY` 不能升级成成功 recipe。比如“SVG 某窗口在 Wan1.3B 此负载失败”不能缩写成“sparse attention 不可用”；“冷启动抵消 compile 收益”不能缩写成“compile 不好”。

等 P2 出现有效外部组件后，再测试经验能否减少第二模型或新硬件上的无效尝试。允许使用 Memory 的组与禁止历史的冷启动组明确分开，不把后者悄悄喂历史阈值。当前尚无跨模型 Memory 收益结论。

## P4：最后再回到完整端到端效率

在方法与质量规则稳定后，比较达到同一可接受目标的墙钟、GPU-hours、API 成本、失败次数和质量。受控 replay 固定工作量；自适应搜索另报告方法差异，不混用。

继续保留每卡任务、实际生成、CPU、传图与 API 时间；将网络重试、上传、服务排队/推理能区分的部分分别计时。API 响应并集不能直接叫网络开销。没有 ready task 时记录阻塞原因，不为制造满卡而多生成视频。

## 本轮之后最值得优先做的两件事

1. 用已保存的 Cache bridge / Wan 组合证据完善质量争议和组件级记忆准入规则。
2. 启动一个不读取历史方法清单的六类 search-only 会话，交付可验证的外部方法候选池；再决定有界 GPU 验证范围。

不应现在承诺“下一轮一小时跑完”或“必定超过 Sol-Agent”。成功标准是可靠地找出额外有效方法，并清楚证明在哪些条件下有效；负结果同样必须交付。
