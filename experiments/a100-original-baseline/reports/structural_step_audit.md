# Dense 50-step / CFG structural audit (pre-freeze)

The p01 progress bar ending at **25/50 is not 25 denoise iterations**. This is a display counter affected by a second-order scheduler. It is not the logical step counter or the DiT-call counter.

Evidence from the unmodified clean SGLang source snapshot (`source/sol_runtime`, commit `16af862a135e27d55bf8e574d786db595a8e0654`, transformer SHA-256 `6a4c853e...`):

1. `.../stages/timestep_preparation.py:141-151` calls `scheduler.set_timesteps(num_inference_steps, ...)` and sets `batch.timesteps = scheduler.timesteps`. The runtime p01 `Sampling params` line records `infer_steps: 50`, 832×480, 81 frames, seed 42, `guidance_scale: 6.0`, and a non-null negative prompt.
2. `.../stages/denoising.py:1251-1261` takes `timesteps_cpu = ctx.timesteps.cpu()`, `num_timesteps = timesteps_cpu.shape[0]`, then executes `for step_index, t_host in enumerate(timesteps_cpu)`. `:1292-1297` updates the progress bar only when `(step_index + 1) % ctx.scheduler.order == 0` (or final step). The checkpoint scheduler is `DPMSolverMultistepScheduler` and p01's 25/50 display is consistent with order 2. No loop uses the display count as a stopping condition.
3. `.../stages/denoising.py:1304-1308` logs average time per step by dividing the elapsed loop time by `len(ctx.timesteps)`. The p01 raw log gives 109.6676 seconds and 2.1933 seconds per step; their ratio is 50.0003. This independently constrains the actual runtime timestep count to 50 at the printed precision. `:1260-1288` performs `_run_denoising_step` once per enumerated timestep, and `:942-970` predicts noise then advances the scheduler once for each.
4. The p01 server args log records `enable_cfg_parallel: false`, `num_gpus: 1`, `warmup: true`, `warmup_steps: 1`, `enable_torch_compile: false`, and no cache config. `schedule_batch.py:317-324` enables CFG when scale >1 and negative prompt exists; p01 logs scale 6.0 and `neg_prompt` length 285. `cfg_policy.py:47-54` builds conditional and unconditional branches. `denoising.py:1413-1430` calls `predict_fn` serially per branch, and `:1391-1409`/`:1622` routes each prediction to `current_model(...)`. Thus the unmodified source implies 2 logical DiT forwards per actual step, or 100 for the 50-step request; this final DiT-call count is **source-derived, not a direct runtime counter**. It must not be represented as observed instrumentation.

The p01 raw log is remote `repo/runs/20260913-091006-sana_video_2b_a100_dense/outputs/prompts/p01/run.log`; independent UTC/monotonic prompt boundaries are in remote `telemetry/events.jsonl`. Final freeze remains conditional on all five prompts and structural video checks. A separate counter-enabled diagnostic would be needed to claim directly observed DiT-call count; no such diagnostic is part of the frozen performance baseline.
