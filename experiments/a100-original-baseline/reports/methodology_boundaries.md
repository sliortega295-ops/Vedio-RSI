# Methodology boundaries for the A100 reproduction

This is the archived Sol-Agent **orchestration-lite** Master/Executor CLI/JSON protocol on archived Harness commit `d2c6407cc9b9133f3fff49fe4b561f14980d3f8b`, with explicit site adaptations for SANA-Video 2B/SGLang, PTY SSH, host-side Codex/job transport, A100 support-kernel fallback, and passive telemetry. It is not a byte-for-byte run of the original 5B/Slurm/Codex-on-node environment. The original `orchestration/prompts/master.md`, technique registry and numeric/method gates remain unchanged; `site_a100_appendix.md` is appended for workload/transport/purity constraints.

The official 5B profile's primary metric is `denoise_s`, secondary `total_s`; the A100 2B profile preserves that ordering and the original speed thresholds and quantitative visual/temporal bounds. The site's frozen `BASELINE.json.total_s=578.02` is the authoritative denominator for the orchestration-lite Master and must match five SGLang request sums; primary denoising time is also recorded (`546.3913 s`). The five requests run sequentially on one UUID per run, not five cards in parallel. The site adapter starts a fresh process/load/warmup for each prompt, unlike the original bundled 5B wrapper; that extra wall/CPU/load cost is site topology, not automatically Sol-Agent decision overhead.

PISA is **NOT_APPLICABLE to the dominant video self-attention path in this reproduction**, so launch scope is `--techs kernel,cache`, not the registry's default three-technique fanout. The pinned video DiT implements ReLU-feature-map linear self-attention with KV aggregation (`source/sol_runtime/.../sana_video.py` `SanaVideoLinearAttention.forward`), whereas `workflow/attention_pa/nodes/codex_executor/pisa_search.md` requires real sparse exact/approximate attention backend phases over QK blocks, defaulting cross/text attention to dense. The DiT does have softmax **cross**-attention; no claim is made that PISA is mathematically impossible there, only that applying the specified default video-self-attention workflow to this linear path would not be faithful without a separate adapter/evaluation. The technique registry was not edited.

The read-only runtime source is a **pre-20260912 dense/off snapshot** (`16af862a135e27d55bf8e574d786db595a8e0654`), not a proven byte-level pristine upstream tree. It contains optional speed flags/APIs predating this search; all were OFF for dense. No old experiment run tree, candidate ledger, report, or candidate-result file was supplied/read in the visible clean stream. However **the allowed archived source/docs themselves contain optimization prior information**: `source/sol_runtime/scripts/sana/sana_video_sglang_run.py:74-86,114-129` describes `--compile` default as `~2.10x` and max-autotune as `~2.56x`; archived `repo/AGENTS.md:106-110` and copied `external/sol_runtime/AGENTS.md:102-106` spell out a SANA fullopt flag recipe. Kernel Executor raw stream attempt01 item27, attempt02 items9/11, attempt03 item13, attempt04 items18/26 actually printed the CLI hints; Kernel attempt01 item9 read archived `AGENTS.md`. Cache attempt01 item11 and attempt04 item18 printed the copied runtime `AGENTS.md`, and attempt03 item34 printed the CLI hints. The archived top-level README also contains a SANA acceleration summary, but the Executor worktree's `README.md` is a minimal generated description; no claim that the top-level README was read follows from those worktree reads. This is **source-contained optimization-hint exposure**, distinct from violating the old-experiment-tree prohibition. Therefore this can be called a fresh frozen-baseline search without old run results, but **not** an unconditional no-history-information or blind-from-zero search. We did not redact allowed source or change ongoing candidates mid-run.

The contaminated seq0001 Master did read Codex memory and is excluded; clean seq0002 Cache attempt 1 later saw old session **file names only** during a broker diagnostic, not old result content. Clean Master attempt1 also exposed old asset path names during LPIPS dependency exploration, without opening historical optimization content. Thus “no old experiment results/recipes read in the visible clean stream” is narrower than “no prior optimization hints.” Generic local skills (`using-superpowers`, `kernel-design-agents`, `ce-optimize`) were read by Executors, a site agent-environment deviation; any extra decisions/gates they induce must be distinguished from archived workflow requirements.

There are two archived workflow contracts in this tree. `workflow/cache_ca/nodes/codex_executor/cache_scope.md` describes a graph executor that exits after a full run, followed by an independent blind Codex reviewer node and `assess_verdict.json`. This execution instead follows `orchestration/prompts/master.md`: a long-lived Executor full loop creates its own delivery/visual evidence, then Master runs the archived independent `orchestration/bin/verify_delivery.py` objective check and its own visual/authenticity review before integration. A graph reviewer is **not** claimed to have run. The graph-created `BASELINE-LOCK.json` was absent on entry to both worktrees. Kernel Executor reconstructed a local `BASELINE-LOCK.json` at 09:42:49 UTC from the frozen goal/run evidence, explicitly recording `graph_lock_present_on_entry=false`; that file is **not** misrepresented as an actual graph-issued lock. Cache has no such file at the 10:45 UTC check. This remains a graph-versus-lite contract mismatch. Any real DELIVERY remains unverified until the archived `verify_delivery.py` executes on its evidence.

The graph/lite ambiguity appeared in live Cache behavior: attempt5 items89/91 said it would exit for an independent graph-style Codex visual reviewer, with no `visual_verdict.json` or `DELIVERY.json`. The attempt exited 10:45:38 UTC. The actual orchestration-lite Master polled the missing delivery and resumed the same Cache identity as attempt6 with a no-download/no-further-cache-run correction while LPIPS is absent; no graph reviewer was spawned or retroactively credited. Cache R02's `150/250` reuse decisions and proposed R03 threshold `0.016` are Executor trace interpretation/prediction; R03 is `NOT_RUN` and neither R01 nor R02 has an admissible quality-gated frontier point.

Kernel R1's visible timeline is different: it collected at 10:44:38 UTC, invoked the archived lossless `plan_eval --no-gemini --no-refresh-collection --assess` by 10:44:54, and at 10:45:21 explicitly treated the generic collector's `baseline_frames_missing` blockers as inapplicable to lossless method correctness. It recorded an authenticity-only verdict and method/structural argument before retaining R1 in `AGENT-STATUS.json` by 10:46:14 and launching R2 at 10:47:26. The visible stream contains **no image-view tool call** between collection and `visual_verdict.json`; that authenticity verdict is self-reported and must be independently checked by Master. Its stated 500 logical DiT calls are the **source-derived structural expectation** (5 prompts × 50 timesteps × 2 CFG forwards), not a direct runtime call counter. R2's FP32→BF16 attention-aggregation change is explicitly allowed by archived Kernel scope as 16-bit execution, but requires actual source/method/structural verification, not acceptance by name alone.

Cache method promotion remains gated by aligned LPIPS plus blind Codex visual quality. The exact `lpips` package is absent from the checked local interpreter/pip cache and remote pinned interpreter/overlay; existing pyiqa is not substituted, no model/dependency download or weight transfer is authorized. Cache timings may be measured, but an LPIPS-blocked Cache point cannot be promoted or integrated as a verified quality point. Kernel structural/method correctness is a separate lossless gate and does not require LPIPS or output closeness, per the archived Master prompt.

All stage times are classified as (1) same-host monotonic observed job/command/marker intervals, (2) source-reported runtime stage timers, or (3) sampled NVML/proc estimates. UTC plus host ID joins local and remote ledgers; local and remote monotonic clocks are never subtracted. Remote NVML GPU app PID can be invisible in the node's `/proc` namespace, so CPU usage is only lower-bounded from visible site-job process ancestry, with unmatched GPU-app process CPU labeled unknown. Observer overhead and gaps are reported independently.

The first Cache candidate and Kernel profile were intentionally allowed to overlap on **different** authorized GPU UUIDs by the Master-controlled two-Executor workflow. This means candidate request timing may share node CPU, filesystem and power/thermal conditions with another job, whereas the dense baseline was solo. Per-job UUID allocation and per-node concurrent load are reported separately; no claim of perfectly isolated A/B conditions follows from the frozen denominator alone.
